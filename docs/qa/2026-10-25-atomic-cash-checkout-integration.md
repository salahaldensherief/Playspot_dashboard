# Dashboard atomic cash checkout integration — 25 October 2026

Status: Draft, targeting `dev`. No production change, merge or deployment.

The `dev` Dashboard called `apply_booking_discount` and then `complete_booking_payment`, allowing a committed discount after a failed collection. It ignored the supplied shift ID, lacked a durable operation ID, and accepted `null` as a successful RPC response. Both discount dialogs sent positive fixed amount and percentage together; some payment actions omitted a shift entirely.

All inspected online cashier booking payment entry points now converge on one `checkout_booking_cash_atomic` call. The active shift is passed from `ShiftCubit` in the booking list, booking card/details, live session, station controls and analytics tile. The data boundary requires an authenticated actor and nonempty shift ID; the backend still verifies ownership, open state and `billing_checkout`. The default amount is `NULL`, so the server calculates remaining cash due after any discount. An explicitly supplied partial amount is converted to integer minor units. The browser persists an operation ID by actor, booking, shift, amount and discount request; retries after an uncertain response use that same ID. The request key is hashed before local persistence. Only a receipt matching booking, shift and operation, with a ledger-row ID and positive collected amount, can produce client success. The dialog waits for that success before closing. The offline cashier's `collectCash` uses a separate permit/sequence protocol and ultimately calls the canonical `collect_booking_cash_partial` receipt path; it does not support discounts and was intentionally left on that server contract.

The new Dashboard requires Mobile/backend Draft PR #84 to be deployed first. Existing production Dashboard remains on its legacy RPC until this branch is deliberately deployed. A client-before-backend rollout would fail every collection; do not deploy it. Existing `complete_booking_payment` is idempotent after a fully paid canonical receipt, but fails closed with `CASH_LEDGER_REQUIRES_CANONICAL_COLLECTION` after a partial canonical receipt. A still-open old Dashboard tab needs an upgrade/reload and manual recovery path for that case. PR #84 also needs its server-calculated remaining-balance revision. The current `dev` Mobile customer checkout uses `create_my_booking_checkout`, not this staff-cash RPC, so its payload is unchanged. Mobile PR #75 is a separate Open Time presentation Draft; PR #83 corrects a completed Open Time partial status. Neither has been merged.

The focused booking payment, atomic HTTP contract and booking action race suites passed **18 tests**; strict Dart formatting and diff checks passed. The isolated exact-schema backend suite passed **12 scenario groups in 10/10 consecutive runs**, including server-calculated remaining after partial collection, legacy-client behavior, lost-ACK replay and blind shift-close reconciliation. The Dashboard tests use mock HTTP; a real signed-in browser with live Supabase remains unverified. Open financial gates: no booking-cash refund/reversal RPC was found in the exact effective schema; combined client staging, cross-tab concurrent partial collection, full cashier permission matrix and shift handover still need verification. Repeating an explicit partial amount with the same operation fingerprint is treated as a replay; an intentionally new second partial payment needs a distinct operation ID and a dedicated UI workflow, which this change does not introduce. Production changes require a restorable backup, recovery rehearsal, client version/rollout plan and the owner's approval for that specific change.

The owner's payment model requires a small verified manual-transfer deposit (or no-deposit cash reservation) and final settlement after play. A rollback-only exact-schema probe found that the current `approve_manual_booking` marks a future 100.00 manual-transfer booking fully paid and posts 100.00 to `payments` and `shift_payments` before play. The current canonical cash collector cannot mix later cash with an existing noncash payment. This Dashboard cash PR does not implement deposit verification or mixed-method final settlement; keep it Draft until a coordinated backend and client contract resolves that gap.
